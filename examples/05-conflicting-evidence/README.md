# Is the software ready to release?

Two teams give conflicting accounts of a software release. Check a readiness report against their notes, the component list and release policy.

**Question:** Does the report have enough evidence for its release-readiness claims?

Upload a component inventory, QA and operations notes, a release policy and an archived verification excerpt. Choose either [the careful report](report-correct.md) or [the report with deliberate errors](report.md) and audit it separately against all files in [sources/](sources/). Include `brief.md` for the supplied review conventions.

The audit can check component counts, conflicting testimony, required approval and whether citations actually support a claim. It reviews the supplied report, including its reasons and citations; it does not write the original report.

The package does not resolve every disagreement or authenticate the signatures. A report citing itself is not an independent review.

These are fictional examples. Keep this guide, the alternate report, metadata, generation files and evaluator material outside the audit input. Evaluator expectations are withheld during a blind audit; the selected report and source documents are always available.

Historical execution records are indexed under [validation/runs](../../validation/runs/). This guide does not constitute a new validation run. Original reports and sources retain their bytes so they can be matched to prior results. New runs belong under `tmp/audit-runs/`, with a separate directory for each report.
