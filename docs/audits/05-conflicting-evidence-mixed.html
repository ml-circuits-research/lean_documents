| A-03 | gateway | gateway-r17-7 |

Rules

  • The brief expressly limits the universe to the three inventory-p2 rows. Exactly three distinct IDs requires both a three-element list and no duplicate IDs.

Assumptions

  • The anchored table is faithfully transcribed and accepted as complete for this exported manifest only.

Reasoning

  1. 1. inventory-p1 identifies the export as the R17 EU-A manifest and explicitly separates manifest entries from runtime measurements.

Limits

  • The proof establishes a finite supplied-inventory fact only. It does not prove completeness of deployment dependencies, runtime instances, build authenticity or source provenance.

Recommended correction or next evidence

CE-04

Evidence: undetermined Argument: invalid_inference Formal: auxiliary

Exact report claim

**CE-04.** Release `R17` on `EU-A` is `Ready` under `POL-4` at the cutoff. Basis: the policy rule in [policy-p2](sources/release-policy.md#policy-p2) proves readiness, and QA records smoke-check success in [qa-p3](sources/qa-attestation.md#qa-p3).

Report anchor: report-ce04

Verification problem

Do the supplied POL-4 implication and QA smoke-check success establish that R17 on EU-A was Ready at cutoff, preserving both required antecedents and the one-way rule?

Evidence used

input/sources/release-policy.md · policy-p1

**policy-p1.** Scope: readiness rule for release `R17`, target `EU-A`, as of the review cutoff. Define `SmokePassed` as all three manifest entries passing the smoke checks; define `SecurityApproved` as an authorized security reviewer approving this release and target; define `Ready` as satisfying this policy's release-readiness criterion.

input/sources/release-policy.md · policy-p2

**policy-p2.** The rule is conditional: if `SmokePassed` and `SecurityApproved`, then `Ready`. This excerpt neither states `SecurityApproved` nor grants security approval. It supplies a sufficient condition, not a necessary-and-sufficient characterization of readiness.

input/sources/release-policy.md · policy-p3

**policy-p3.** Evidence from QA and Operations must retain separate provenance. This excerpt assigns neither source priority and supplies no rule for deriving approval from the absence of a rejection or from a later document timestamp.

input/sources/qa-attestation.md · qa-p3

**qa-p3.** The three manifest entries `A-01`, `A-02`, and `A-03` passed the release smoke checks. This document does not assert that all security review requirements passed.

input/sources/release-inventory.md · inventory-p2

**inventory-p2.** The complete manifest-entry table for this export is:

| Entry ID | Component | Build identifier |
| --- | --- | --- |
| A-01 | api | api-r17-9 |
| A-02 | worker | worker-r17-4 |
| A-03 | gateway | gateway-r17-7 |

Rules

  • policy-p2 states only (SmokePassed AND SecurityApproved) implies Ready. It neither asserts approval nor provides a converse or a necessary-and-sufficient definition.
  • An implication can establish its consequent only when its full antecedent is available. policy-p3 supplies no approval-from-silence or priority rule.

Assumptions

  • For evaluating the proposed argument, grant the attributed QA smoke-check assertion for all three manifest entries as its SmokePassed premise. This does not authenticate QA or invent security approval.

Reasoning

  1. 1. The inventory gives the same three entries referenced in qa-p3, so the smoke-success premise has documentary support for the finite population.
  2. 2. policy-p1 defines SecurityApproved as an authorized reviewer approving this release and target. policy-p2 expressly does not grant or assert it; qa-p3 does not assert all security requirements passed. The corpus supplies no established approval premise.
  3. 3. The report incorrectly treats a two-premise conditional plus one premise as enough to infer Ready. The conditional theorem shows what would follow if both premises were independently available.
  4. 4. A model with SmokePassed=true, SecurityApproved=false and Ready=false satisfies the policy and the supplied smoke premise, so these premises do not entail readiness.
  5. 5. A second model with SmokePassed=true, SecurityApproved=false and Ready=true also satisfies this sufficient-only policy. Hence neither missing approval evidence nor this rule proves actual non-readiness.

Limits

  • The countermodel refutes the report's entailment claim, not the actual Ready proposition. SecurityApproved=false is hypothetical rather than inferred from missing records. The conditional theorem is not an executed certification of this release.

Formal evidence

Audit.conditionalReadiness — auxiliary

∀ (Smoke Security Ready : Prop), ((Smoke ∧ Security) → Ready) → Smoke → Security → Ready

Audit.claim04MissingPremise — auxiliary

Audit.policy true false false ∧ Audit.policy true false true ∧ ¬ ((Audit.policy true false false ∧ true = true) → false = true)

Recommended correction or next evidence

State the missing authorized-security-approval premise and obtain source-linked evidence for it before applying this rule; leave actual readiness undetermined on the supplied argument.
